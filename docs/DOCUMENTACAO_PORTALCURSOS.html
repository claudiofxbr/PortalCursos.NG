1. Resumo Executivo

O PortalCursos.NG é um ecossistema educacional de ponta, desenvolvido em arquitetura isolada de alta fidelidade e robustez operacional. Unificando o poder do framework Spring Boot (Java 17) no ecossistema de retaguarda e a responsividade do Next.js (React 18/19) no portal do usuário, o sistema garante conformidade rigorosa com segurança de dados, integridade de cadastros e velocidade excepcional sob carga de tráfego.

Estabilização OMEGA-SUPREME
A arquitetura resolve de forma definitiva o problema de acoplamento entre os tipos de matrículas estudantis através de uma unificação física no banco de dados relacional e encapsulamento em contêineres virtuais.

2. Visão Geral do Produto

A plataforma serve como o hub administrativo e acadêmico para o gerenciamento de estudantes matriculados em cursos de Graduação e Pós-Graduação da instituição. O sistema lida com a captura de documentos, verificação de fotos de identificação, trilha de auditoria financeira de mensalidades e homologação de grades curriculares e código IES no e-MEC.

Objetivos Estratégicos

  • Unicidade Cadastral Global: Prevenção absoluta de cadastros duplicados de e-mails ou CPF utilizando validação ativa sem filtros lógicos no banco de dados.
  • Resiliência de Infraestrutura: Minimização a zero de indisponibilidades por meio de empacotamento Docker local e injeção redundante de ambiente de produção.
  • Garantia de Performance: Carregamento instantâneo de páginas e respostas de API em sub-segundos, mesmo em servidores remotos compartilhados.

Camada de Persistência de Estudantes

O sistema adota o padrão de mapeamento de herança de banco de dados Single Table Inheritance do Hibernate/JPA. Isso agrupa estudantes de Graduação e Pós-Graduação na mesma tabela física students, garantindo a unicidade e indexação de campos de auditoria em uma única consulta.

@Entity
@Table(name = "students")
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "student_type", discriminatorType = DiscriminatorType.STRING)
public abstract class BaseStudent { ... }

Configurações do Pool de Conexões Hikari (Neon Serverless)

Para atenuar desconexões abruptas provocadas pela ociosidade inerente de provedores de banco de dados serverless (Neon.tech), o pool Hikari foi configurado da seguinte forma:

spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.minimum-idle=3
spring.datasource.hikari.connection-timeout=120000
spring.datasource.hikari.keepalive-time=45000
spring.datasource.hikari.connection-test-query=SELECT 1

5. Governança & Codificação

Para assegurar que o PortalCursos.NG permaneça sustentável e de fácil manutenção ao longo dos anos, as seguintes regras são aplicadas de forma inflexível:

Boas Práticas de Codificação

  • Higienização Automática: Todos os campos de identificação numérica como CPF e números de telefone passam por limpeza Regex obrigatória (replaceAll("[^0-9]", "")) antes de qualquer persistência no banco.
  • Exclusão Lógica Sem Conflitos: Métodos de verificação de cadastro único como existsByEmailGlobal e existsByCpfGlobal ignoram filtros @Where(clause = "active=true") para evitar que um CPF inativo seja duplicado no banco.
  • Tratamento Centralizado de Exceções: O uso de blocos try-catch vazios é expressamente proibido. Toda exceção transacional deve disparar rollback completo (@Transactional(rollbackFor = Exception.class)).

6. Processo de Git & GitHub

O fluxo de desenvolvimento da equipe baseia-se em um modelo simplificado e rigoroso de ramificações (Git Flow), projetado para blindar a estabilidade da branch principal de produção.

Políticas de Branches

  • main: Código puramente de produção. Protegida contra pushes diretos.
  • develop: Branch estável de homologação acadêmica e testes de integração.
  • feature/nome-recurso: Branches curtas criadas para o desenvolvimento de tarefas específicas.

Fluxo de Code Review e Pull Request

  1. O engenheiro cria uma ramificação feature/sua-feature a partir da develop.
  2. Após finalizar e validar localmente, abre-se um Pull Request direcionado à branch develop.
  3. A branch é submetida a compilação obrigatória e análise de integridade estática.
  4. Pelo menos uma aprovação de Engenheiro Sênior ou Tech Lead é requerida antes do merge.

7. Protocolo de Deploy VPS

O deploy é orquestrado de forma totalmente automatizada por meio do painel interativo local do Windows deploy-vps.ps1 e executado na VPS Hostinger sob o script blindado deploy_docker_compose.sh.

Bloqueio Automático do Nginx
Durante o deploy, o script desativa temporariamente outros servidores conflitantes (como Apache ou EasyPanel) que ocupam as portas HTTP/HTTPS (80/443), para garantir que o Nginx assuma a escuta do host principal de forma exclusiva.

Passo a Passo da Implantação

  1. Compilação e Limpeza Local: O PowerShell compacta as pastas backend, frontend, devops e database limpando dependências pesadas de desenvolvimento (node_modules e target).
  2. Injeção de Ambiente Segura: Lê o domínio final (ex: xavierbr-vps.tech) e injeta um .env com as rotas HTTPS devidamente corrigidas para o Nginx da VPS.
  3. Transferência Compacta: Envia o pacote app-deploy.zip via SCP para a pasta /tmp da VPS da Hostinger.
  4. Instalação Remota e Isolamento: Extrai os fontes limpos, encerra instâncias de containers órfãos, reconstrói as imagens locais com --no-cache e sobe a pilha produtiva.
  5. Geração Automática de SSL: Roda o Certbot Let's Encrypt para configurar HTTPS seguro definitivo sob o domínio configurado.

8. Segurança & Monitoramento

O PortalCursos.NG implementa um sistema robusto de barreiras físicas e lógicas de proteção de dados.

Mecanismos de Defesa

  • Firewall UFW Blindado: Portas expostas no contêiner do banco ou das portas originais do Node/Java são inacessíveis externamente. Apenas as portas de controle seguro 22, 80 e 443 estão abertas na VPS Hostinger.
  • Gatekeeper Local (7512): Um componente global no frontend (SecurityGate) bloqueia renderizações caso o token de acesso 7512 esteja ausente no cache do navegador.
  • Segurança JWT e CORS: Autenticação baseada em tokens com tempo de expiração curto (15 minutos) e expiração longa do cookie de atualização, blindando a API contra ataques Cross-Site Scripting (XSS).

9. Estratégia de Testes

Nenhuma versão é considerada pronta para homologação sem cumprir as metas mínimas de testes do pipeline de qualidade do QA Lead:

Checklist de Validação Acadêmica

  • [ ] Testes Unitários: Cobertura total das lógicas de validação de CPF e cálculo acadêmico no Spring Boot (./mvnw test).
  • [ ] Testes E2E: Validação automatizada do fluxo de ponta a ponta de matrículas via scripts Playwright simulando inserções de dados e uploads reais de fotos.
  • [ ] Teste de Carga do Nginx: Execução de testes de estresse com concorrentes simulados usando Apache Benchmark para verificar se há vazamento de memória ou travamento do Hikari Pool.

10. Plano de Contingência

Para mitigar falhas catastróficas ou corrupção de dados da plataforma em produção:

Políticas de Rollback e Backup

  • Backup do Banco de Dados PostgreSQL: O script automatizado backup_db.sh realiza dumps periódicos dos volumes do banco Docker e armazena em diretórios criptografados no host local da VPS.
  • Rollback Instantâneo de Containers: Caso uma nova imagem apresente bugs pós-deploy, o time de infraestrutura pode retornar à versão estável anterior em segundos rodando: 
    docker compose -f docker-compose.prod.yml rollback
